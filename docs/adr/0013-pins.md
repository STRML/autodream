## apply-pins exits 0 whatever happened to the pins, and exits 3 only when its counters cannot be trusted

Status: accepted · Date: 2026-11-21 · Code: `bin/apply-pins.sh` (`write_result`, the `RESULT` clear, the `CONTENT` read)

### Context

A pin must never cost a report. `run.sh` logs whatever `pins-result.txt` it finds, so an earlier run's counters standing in for this run's would read as this run's. A redirect on the read loop that fails to open runs zero iterations, and the counters would then say L2 proposed no pins.

### Decision

- Exit 2 on bad arguments. Exit 3 when `pins-result.txt` cannot be cleared or written, so the caller does not read stale counters as current. Otherwise exit 0 whatever happened. The counters (`pins-result.txt`, one `key: value` per line) say what went wrong.
- The old `pins-result.txt` is removed before anything else. If it cannot be cleared, the script stores nothing and exits 3.
- `pins.jsonl` is read once into `CONTENT` and that read is checked. A failed read sets `unreadable=1`, writes the counters, leaves the pins in place, and exits 3 only if the counters could not be written.
- A missing CLI sets `cli_missing=1`, counts the non-blank lines as `total`, and leaves the pins in `pins.jsonl`.

### Consequences

A new failure mode becomes a counter and a `write_result` line, not a nonzero exit. The one exit that blocks the caller is 3, and it means the counters are not this run's. `tests/apply-pins.sh` pins these paths.

## a pin tagged with a harness is stored only when the installed shared-memory proves it filters on the tag

Status: accepted · Date: 2026-11-21 · Code: `bin/apply-pins.sh` (`GATE_OK` probe, `apply_line`)

### Context

A pin may carry `harness` (`claude`, `omp` or `codex`), stored as `metadata.harness`. The tag is safe only when the installed `shared-memory` filters on it at startup. Without that filter the pin would load into every harness.

A bare `--host` fails closed in a `shared-memory` built with the harness gate (agent-mnemopi PR 12) and is ignored by an older one, so the error text tells the two apart without storing anything.

### Decision

Before the pin loop, the script runs `shared-memory startup --host` with stdin from `/dev/null` and sets `GATE_OK=1` only when the output contains `--host needs a harness name`. When `GATE_OK` is not 1, a pin with a `harness` field is held, counted as `unsupported_harness`, and not stored. Pins without a harness are unaffected.

### Consequences

If agent-mnemopi changes that error text, the probe reads every installation as the old build and holds every tagged pin. The `pins_unsupported_harness` counter in `pins-result.txt` is where that shows. Change the probe and the CLI together.

## the pins ledger never guesses, so every doubtful case stores nothing or becomes its own outcome

Status: accepted · Date: 2026-11-21 · Code: `bin/apply-pins.sh` (`apply_line`)

### Context

`pins-applied.tsv` holds `<sha1 of the resolved bank and the canonical pin><TAB><memory_id>` per stored pin. A pin already listed is skipped, so a rerun skips it, except after an `unledgered` write (below). A failed call writes no row, so a rerun of the same date retries it. `run.sh`'s `sweep_stranded_pins` reruns the script for any date in the trailing week whose counters show failed pins.

Several ways of reading the ledger look like "not stored yet" when they are not.

### Decision

- An empty hash is refused. `cut` succeeds even when `shasum` dies, and an empty hash, once ledgered, would make every later pin in the file look like a duplicate. The hash must match `^[0-9a-f]{40}$`.
- A ledger that exists and cannot be read is `failed`, because reading it as empty would store the pin again. When duplicates cannot be ruled out, nothing is stored.
- An empty `memory_id` is `failed`. It is not a stored memory anyone can find, and ledgered it would block every retry.
- A ledger row that cannot be written after the memory is stored is its own outcome, `unledgered`, never `applied`. The id goes to the run log so the duplicate a rerun will create can be found and removed.

### Consequences

The counters separate `failed` (nothing stored, retryable) from `unledgered` (stored, will duplicate on rerun). Merging them hides a duplicate-memory risk. `tests/apply-pins.sh` pins each row of the failure matrix in `docs/plans/2026-09-15-mnemopi-pins.md`.

## a pin is stored only into the bank its project's own directory names, and a project matches by exact value

Status: accepted · Date: 2026-11-21 · Code: `bin/apply-pins.sh` (`project_cwd`, `apply_line`)

### Context

`pin-projects.tsv` (`project<TAB>cwd`, written by `run.sh` for every project the run triaged) is the authorization list: a pin naming any other project is refused. A model writes the project name in each pin.

`mnemopi_remember` takes its bank from the payload, then `MNEMOPI_MCP_BANK`, then `"default"`, and never from `--cwd`. A call that passes only `--cwd` lands every pin in the global store.

A forced rebuild can resolve a project to a different directory (`/tmp/a_b` and `/tmp/a-b` encode alike), and a pin stored in one bank is not stored in the other.

### Decision

- `project_cwd` passes the project to awk through `ENVIRON`, not `awk -v`. `-v` expands backslash escapes, so a model-written project could match a row it does not name.
- `apply_line` asks `shared-memory context --cwd <cwd>` for the project's `retainBank` and names it in the `mnemopi_remember` payload. No bank means no store: the pin counts as `failed` and stays retryable.
- The `context` output is captured into a variable first, so the call's own exit status counts. Piped straight into `jq`, only `jq`'s status would.
- The bank is part of the pin's identity: the ledger hash is the sha1 of `<bank>\n<canonical pin>`.

### Consequences

Changing the awk call back to `-v`, or dropping the bank from the payload or the hash, reopens a silent wrong-store or wrong-match path with no error. `tests/apply-pins.sh` and `tests/mock-shared-memory.sh` pin the bank rules (`MOCK_SM_MODE=ctxexit`: `context` prints a valid `retainBank` but exits 1). Plan and failure matrix: `docs/plans/2026-09-15-mnemopi-pins.md`.

## a pin counts as stored only on exit 0 with status stored, or on mutation_committed_journal_incomplete

Status: accepted · Date: 2026-11-21 · Code: `bin/apply-pins.sh` (`apply_line`)

### Context

`shared-memory call mnemopi_remember` exits 1 with status `mutation_committed_journal_incomplete` when the write committed but its journal append failed. That memory exists and has an id. Calling it a failure would store it again on the next run, so the exit status alone cannot decide the outcome.

The script reads `pins.jsonl` on a separate fd, but a CLI that reads stdin must never be able to swallow the pins after the current one.

### Decision

- Both `shared-memory` calls (`context` and `call mnemopi_remember`) run with `</dev/null`.
- The output is parsed with `jq`, with the exit code passed in. A memory is stored when `status == "stored"` and the exit code is 0, or when the status is `mutation_committed_journal_incomplete`, the one status that may pair a nonzero exit with a stored memory. Anything else is `failed` and stays retryable.
- For the journal-incomplete status the script logs `stored <id>, but shared-memory reported mutation_committed_journal_incomplete` to stderr and still ledgers the pin.

### Consequences

A new shared-memory status that commits a write with a nonzero exit has to be added to the `jq` select, or its pins are stored again on every rerun. `docs/adr/0013-pins.md#the-pins-ledger-never-guesses-so-every-doubtful-case-stores-nothing-or-becomes-its-own-outcome` covers what happens after the status is read.

## memory pins run right after the streak update, only behind a complete report from this run

Status: accepted · Date: 2026-11-22 · Code: `bin/run.sh` (`run()`: the `PINS` block; `write_pin_projects`, `restore_pins_ledger`, `apply-pins.sh`); plan `docs/plans/2026-09-15-mnemopi-pins.md`

### Context
- Ordering: pins are the first step after the report that calls out (the streak update only writes a local file), ahead of `notify.sh` and the consume steps. `notify.sh` runs `AUTODREAM_OPEN` synchronously, so a blocking editor command holds the run there; if the run dies in that wait, the next run skips the date and pins placed after it are never stored.
- Gating: pins need a complete report from THIS run behind them: `report_complete`, `CONSUME_SAFE` (cleared when the old report could not be moved aside), and `PINS_SAFE` (cleared when an earlier `pins.jsonl` could not be moved aside). They skip the consume date gate on purpose: an old-date rebuild still teaches something real, and `apply-pins.sh`'s ledger stops a rerun from storing the same pin twice.
- `pin-projects.tsv` is the authorization list. It holds only projects this run triaged, each with the working directory its session's adapter resolved, so a pin naming any other project is refused and memory is never scoped by a path the model wrote.

### Decision
The chain of `elif`s skips, with a logged reason, when the gates fail, when `pin-projects.tsv` cannot be written, or when the ledger cannot be restored (duplicates cannot be ruled out); otherwise it runs `apply-pins.sh` and logs the counters; if `apply-pins.sh` exits non-zero it logs that the counters are unavailable (check `pins-applied.tsv` for what was stored) and the unstored pins stay in `pins.jsonl`. See docs/adr/0001-runner-lifecycle.md#background-where-state-lives, "Where state lives" (`pin-projects.tsv`, `pins-applied.tsv`).

### Consequences
Do not apply pins from a stale or unvalidated `pins.jsonl`. Do not gate them on the normal-nightly-date rule used for consuming.

## The pin authorization list and the pins ledger are held in the runner's memory before any model runs

Status: accepted · Date: 2026-11-22 · Code: `bin/run.sh` (`run`: `PIN_PROJECTS_*`, `SESSION_ROWS`, `PINS_LEDGER_*`)

### Context
L1 workers run with the Write tool and `bypassPermissions`, so any file they can reach they can rewrite: `sessions.txt`, `sessions-source.txt`, findings JSON. (The original code comment says L2 holds Write too; that is stale, L2 is read-only (`Glob Read`) now, which is why only L1 is the writer here.) A worker could also empty `pins-applied.tsv`, after which the apply step would store every pin again. See docs/adr/0001-runner-lifecycle.md#background-where-state-lives, 'findings/YYYY-MM-DD/pin-projects.tsv' and '`pins-applied.tsv`'.

### Decision
- Before the first model call, `session_rows` builds `SESSION_ROWS`, and `PIN_PROJECTS_TSV` and `SESSION_CWDS_TSV` are derived from it; they stay in this shell's memory until the pins are applied after the report. If any step fails, `PIN_PROJECTS_BUILT` stays 0 and the run stores no memory pins.
- The ledger's content is read into `PINS_LEDGER_SNAPSHOT_X` and put back before the pins are applied. A ledger that exists but cannot be read leaves nothing to restore from, so `PINS_LEDGER_OK=0` and this run stores no pins.
- The ledger is read with `cat ... && printf x`: the trailing `x` keeps `$(...)` from stripping the ledger's final newline.

### Consequences
- Do not rebuild the project list or re-read the ledger after L1 or L2 from disk.
- The trailing `x` must be stripped when the snapshot is restored; removing it silently drops the last newline of the ledger.

## A project gets a pin cwd only when all its sessions agree on one usable cwd

Status: accepted · Date: 2026-11-22 · Code: `bin/run.sh` (`pin_projects_from_rows`, `write_pin_projects`)

### Context
Anything looser stores one project's pin in another project's bank: a transcript sitting in a bucket its cwd does not encode to, or two directories that encode to one bucket (`/tmp/a_b` and `/tmp/a-b`).

### Decision
`pin_projects_from_rows` reads `session_rows` output on stdin and prints one `project<TAB>cwd` row per project. The cwd is filled only when the project has exactly one distinct cwd and it is not `?`; an unusable `?` still counts as a distinct cwd, so it makes the project ambiguous rather than vanishing. A project with no usable cwd keeps an empty column, and `apply-pins.sh` refuses its pins as `no_cwd`. `write_pin_projects` removes the old `pin-projects.tsv` first, so an authorization list from an earlier run never outlives a failed write, and fails when the build itself failed.

### Consequences
This file is the pin authorization list: do not loosen the single-cwd rule or build it from anything a model could have touched.

## A nightly sweep re-applies pins that a complete report left unstored

Status: accepted · Date: 2026-11-22 · Code: `bin/run.sh` (`sweep_stranded_pins`, `lock_held_by_live_run`)

### Context
Pins can be stranded after a complete report: the run died between the report landing and the pin step (issue 72), or a store call failed or the CLI was missing and no one reran that date (issue 69). Nothing else revisits an old date: the nightly only processes yesterday and the idempotency guard skips a date that has a report.

### Decision
`sweep_stranded_pins` looks at findings dirs in the trailing window (`AUTODREAM_UNASSEMBLED_WINDOW`, default 7). A dir qualifies when it holds a non-empty `pins.jsonl`; the `pin-projects.tsv` the proposing run wrote (the authorization list, never rebuilt here from files a model could have touched); a complete report no older than the pins (an older report is not the one behind them); and either no `pins-result.txt` or counters (`pins_failed`, `pins_cli_missing`, `pins_unreadable`, `pins_unsupported_harness`) above zero. The pins ledger makes the rerun safe: a pin already stored is a duplicate. A pin that cannot be stored is retried each night until its date leaves the window.

Skips, each for a reason:
- A forced rebuild of the target date (`AUTODREAM_FORCE=1`) is left alone: the rebuild replaces its pins and owns them.
- A date whose run lock is held by a live pid is left alone (`lock_held_by_live_run`, which only reads and never reclaims). `autodream-now.sh` runs under a different launchd label, so another date's run may be in its pin step right now, and two `apply-pins` on one date both read the ledger before either appends and store a pin twice.
- A `pins-result.txt` older than the pins describes an earlier run of the date (a forced rebuild replaced the pins and died before applying them), so it settles nothing.
- Pins with no `pin-projects.tsv` are logged and stay in `pins.jsonl`, because no project is authorized.

### Consequences
Never rebuild the authorization list in the sweep. If the lock scheme changes (see `per-date-run-lock-mkdir`), `lock_held_by_live_run` reads the same `pid` file and must change with it.

## an earlier pins.jsonl is moved aside before every L2 attempt

Status: accepted · Date: 2026-11-22 · Code: `bin/run.sh` (`run()`: `STALE_PINS`, `PINS_SAFE`)

### Context
A `pins.jsonl` already present came from an earlier run or an earlier attempt, and no complete report from THIS attempt stands behind it. Left in place, a dead attempt's pins would be stored alongside the next attempt's report. The name comes from `mktemp`, not a timestamp: two forced rebuilds inside one second would otherwise pick the same name, and the second move would overwrite the first run's unapplied pins.

### Decision
Moved to `pins.jsonl.stale-XXXXXX`, not deleted, so a pin that never reached Mnemopi stays readable. A failed move clears `PINS_SAFE` for the run, for the same reason `CONSUME_SAFE` works that way (see `stale-dream-moved-aside-before-l2-and-consume-safe`), and removes the empty `mktemp` placeholder it left behind, which would otherwise be litter once per attempt.

### Consequences
Do not replace the `mktemp` with a timestamp. Nothing in the runner reads a `pins.jsonl.stale-*` file again; it is a record only. A `pins.jsonl` that stands beside a finished report and never finished storing is a different case, handled by `sweep_stranded_pins`.

## pins.jsonl and pin-projects.tsv are written before the report is staged

Status: accepted · Date: 2026-11-22 · Code: `bin/run.sh` (`run()`: `write_pin_projects`, ordering of the pins block ahead of the `REPORT_PATH` staging; `sweep_stranded_pins`)

### Context
A report that stands complete on disk must always have, whenever L2 proposed pins and `PINS_SAFE` held, its `pins.jsonl` and `pin-projects.tsv` beside it, so a kill after the report lands cannot leave a complete report whose pins were never proposed (issue 72). A kill before the report lands leaves no complete report, and the rerun moves these aside and asks L2 again. The authorization list goes to disk with the pins so a later run can still apply them if this one dies before the pin step (see `sweep_stranded_pins`).

### Decision
The pin block is extracted and `write_pin_projects` runs before the report body is written. A failure to write `pin-projects.tsv` logs that the pins wait for a later run that can.

### Consequences
Reordering these steps reintroduces the window in issue 72: report on disk, pins lost, and the next trigger skips the date.

## The findings `project` field is overwritten deterministically from the runner's own session rows

Status: accepted · Date: 2026-11-22 · Code: `bin/run.sh` (`run`, the python3 block after the oversized loop)

### Context
SESSION_TRIAGE.md asks the L1 worker to emit `project` by hand, and haiku does it nondeterministically: one run surfaced the SAME `-Users-sean` dir as `-Users-sean`, `Users-sean` (dash stripped), and even the bare session UUID (filename, not dir). That splinters L2's per-project grouping.

### Decision
The project is the bucket the runner already computed for each session in `SESSION_ROWS` (see `session_rows`) before L1 ran. Each findings file is looked up by its own name, the session hash, never by the `session_path` the model wrote, and its `project` field is overwritten, atomically (temp file plus `os.replace`). Malformed JSON and non-object JSON are left for the triage-failures report section. It is idempotent on re-runs. Without `python3` the step is skipped with a log line (L2 grouping may show dupes). A nonzero exit from the block logs a WARNING that some findings keep the project the L1 model wrote.

### Consequences
- Do not key the lookup off anything in the findings JSON, which the model wrote.
